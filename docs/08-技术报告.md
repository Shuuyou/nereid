## 重要内容预览

**一句话定位**：捞针 · Nereid 是一套以 LangGraph 三层混合智能体编排为中枢的 AI 安全情报系统——它把散落在 41 个数据源里的 CVE 漏洞、非 CVE 事件（提示注入/投毒/Agent 滥用）与中文政策法规，经四层去重、8 维并发富化、向量+图谱双知识底座沉淀后，变成可以追问、可以溯源、可以解释的情报卡片与多跳问答。**用 AI 原生架构，做 AI 安全的情报。**

**系统总体架构（缩略）**：

```
 表现层    Next.js 14：态势大屏 │ 情报卡 │ 图谱探索 │ 深度问答 │ 报告 │ 源健康
──────────┬─────────────────────────────────────────────────────────────────
          │ REST + SSE
 智能体编排层 LangGraph：Pipeline DAG（采集→去重→富化→索引→图谱→推送）

# 第 1 章 需求分析与设计目标

## 1.1 赛题解构：AI 安全情报 ≠ 通用漏洞库

赛题九要求构建"智能体驱动的 AI 安全知识情报系统"。我们对命题意图的三点解读：

1. **情报对象的重新定义**。AI 安全的"漏洞信息"不止 CVE 编号漏洞——提示注入、越狱、数据投毒、模型窃取、Agent 滥用、AI 供应链污染等大量威胁没有 CVE 编号；同时中国场景下的政策法规（网信办规定、TC260 标准、GB 国家标准）同样是必须被监测、结构化、可问答的"情报"。因此系统必须做 **CVE + 非 CVE 双轨**。
2. **智能体是真考点不是贴标签**。评分表单列"智能体架构"15 分，考察的是编排模式与任务性质的匹配——哪些环节该确定性、哪些环节该自主决策、状态如何持久化、人机如何协同，而非"调了某个 Agent 框架的 API"。
3. **工程落地是分水岭**。时效、准确率、自动化、可部署、可观测，这些评分点全部要求"真跑起来的系统"，而不是设计文档。

**现实中的三大痛点**（命题方与用户的共同问题）：

- **信息过载**：CVE 年发行量已超 4 万条/年量级，叠加厂商公告、社区文章、论文，人工阅读不可行；
- **渠道分散**：权威库、厂商 CSAF、邮件列表、中英文社区、政策发布页各自为政，同一事件反复出现；
- **缺乏问答与关联**：传统漏洞库只能"查编号"，无法回答"我们内网跑了 Ollama 和 Milvus，风险如何"这类跨文档问题。

## 2.2 端到端数据流

```
源(S) ──pull──> 采集器 collect(source) ──> (items, new_state)

      ▼

      │
      ▼

      ▼

## 2.4 架构层面的三个关键决策

1. **PostgreSQL 为唯一事实源**：Item 及其全部富化字段落 PG（含 JSONB `enrichment`/`extra`），Qdrant 与 Neo4j 都是从 PG 派生的"读侧投影"——任何时刻重建索引/图谱都不会丢数据，三库状态可独立修复。
2. **采集与富化解耦**：采集链路（ingest）只负责"快、稳、不重"，重活（富化/索引/图谱）全部推给后台 `_post_process` 与调度任务，保证源侧吞吐不受 LLM/外部 API 限速影响。
3. **一切皆可降级**：所有外部依赖（LLM、测绘、论文库、各数据源）都有降级路径，降级产出必须显式标记（`is_simulated`、`status: partial`），详见第 10 章降级矩阵。

> **评委看点**：架构图一图说清"智能体在哪、数据怎么流、哪些是真能力"；2.4 的三个决策体现的是工程权衡而非名词堆砌。本章是文档分的核心产出章。

# 第 3 章 智能体方案设计

> 本章是"智能体架构 15 分"的主战场。核心主张：**不是"用了 Agent 框架"，而是按任务性质选择编排模式**——三种任务、三种图拓扑、一种统一的工程底座。

## 3.1 三层混合编排架构

| 链路 | 任务性质 | 编排模式 | 实现 | 为什么这样选 |
|---|---|---|---|---|
| 周期链路 | 采集→去重→富化→入库，要求幂等、可重放、部分失败可续跑 | **确定性 DAG** | `agents/pipeline_graph.py`：collect→enrich→index→kg→notify 五节点 StateGraph | 批量处理的最差选择才是"让 LLM 决定下一步"；确定性图保证每一步可审计、可重放、可断点续跑 |
| 交互链路 | 问答，问题空间开放，需要按需取证据 | **Supervisor-as-Tools** | `rag/query_agent.py`：DeepSeek function calling 自主调用 4 个工具（≤2 轮），证据不足回退确定性检索 | 开放问题无法预先画死路径；但完全自治不可控，故设轮次预算+确定性回退双保险 |
| 分析链路 | 日报/专题报告，需要质量自校 | **Planner-Executor-Critic** | `agents/analyst.py`：聚合统计→提纲→逐节撰写→校验回环；LLM 不可用时确定性模板兜底 | 报告质量主观，需要"写-评-改"回环；同时统计口径必须确定性（数字不许 LLM 编） |

**图 3-1 三层混合编排架构图**（三条链路共享同一套存储与工具层，状态互不污染）。

## 3.2 状态与记忆

- **运行态持久化**：每次 DAG 执行写入 `TaskRun` 表（任务名/状态/明细），同时经 `pipeline:run:{run_id}` Redis hash 逐节点回写实时状态——前端轮询到的是真实节点进度而非定时器动画（`GET /api/pipeline/run/{run_id}` 可查）。
- **中间态共享**：问答链路的检索证据、KG 事实、trace 步骤以结构化 dict 在节点间传递；多轮对话历史经 `session_id` 关联（`GET /api/qa/sessions/{session_id}`）。
- **HITL 人机协同**：富化结果按置信度自动分流——全 error≥3 维或平均置信度 <0.4 的条目自动置 `review_status=needs_review` 进复核队列（`GET /api/review`），人工确认/回炉走 `POST /api/review/{id}/{confirm|reject}`，闭环可审计。

## 3.3 工具生态与契约

QueryAgent 工具集（`AGENT_TOOLS`，DeepSeek tools 协议）：

| 工具 | 输入契约 | 输出契约 | 底层实现 |
|---|---|---|---|
| `retrieve_intel` | `query:str, top_k:int` | item 级证据列表 `{item_id,title,url,text,score}` | dense+sparse RRF 混合检索 |
| `kg_expand` | `entities:[str], hops:int≤3` | 图谱事实 `{item_id,title,rel,via_cwe}` | Neo4j 参数化 Cypher 有界扩展 |
| `get_item_detail` | `cve:str` | 完整情报卡（评分/PoC/映射/攻击链/富化摘要） | PG 三表联查 |
| `list_kev` | `limit:int` | KEV 在野利用清单（AI 相关度排序） | PG `is_kev` 直查 |

**表 3-1 智能体工具清单与契约表**。工具输出统一封装为 `{kind,title,summary,evidence}`——`summary` 回灌给模型决策是否继续，`evidence` 进入证据池参与重排与引用。

## 3.4 防坑设计（真实工程深度）

1. **Agent 轮次预算**：工具调用循环硬上限 2 轮（`for rnd in range(2)`），模型无 tool_calls 即提前终止——防止"为了调用而调用"的成本失控；
2. **证据不足自动回退**：Agent 证据 <2 条时自动走确定性子问题并行检索兜底（`fallback_retrieve`），保证"Agent 摆烂也有答案"；
3. **Supervisor 上下文只回结论**：工具返回给模型的是 ≤1200 字符的 summary 而非全文，防上下文爆炸；
4. **节点幂等**：ingest 按 `(source_id, native_id)` 幂等、index 按内容哈希跳过、KG 用 MERGE、子表 delete+insert——任何节点重跑不产生脏数据；
5. **CVE 直连短路**：问题含 CVE 编号时绕过整条 RAG 链直查情报卡，2–3 秒返回高置信答案（trace 里体现为 `cve_direct` 单步）。

**图 3-2 QueryAgent 调用序列（真实 trace 摘录）**：以"我们内网部署了 Ollama 和 Milvus 2.4…"一题为例，`trace.steps` 实测 10 步：`extract → route → tool_call(retrieve_intel ×N) → tool_call(kg_expand) → agent_evidence → retrieve → kg_expand → context → generate`，耗时 20.4s，命中 4/4 期望关键词（详见第 11 章逐题表）。

> **评委看点**："多角色协作 + 自主编排 + 架构精良可扩展"优秀档三连——三层混合是对任务性质的回答而非框架展示；防坑设计和真实 trace 证明不是概念图，这是本章拉开差距的关键。

## 4.3 采集器契约与统一 ingest

所有采集器实现统一契约：`collect(source) -> (list[RawItemData], new_state)`，由 `registry.run_source` 统一调度，负责：

- **增量游标**：`source.state` JSONB 记录 lastMod 时间戳/ETag/git commit，重启续采不回头；
- **失败重试与降级**：`consecutive_failures` 计数 + `last_error` 留痕；cisa.gov 直连不可达时 KEV 自动切 `raw.githubusercontent.com/cisagov/kev-data` 镜像；GitHub API 403 时 GHSA 标记等待 token 不阻塞全链路；RSS 被 WAF 拦截记错不阻塞；
- **状态留痕**：每次执行写 `TaskRun`，指标进 Prometheus（`secagent_items_collected/new/merged`、`collection_duration`、`source_lag`），前端「数据源」页实时展示健康度（实测 42 条记录中 37 个健康）。

## 4.4 四层去重流水线

41 个源必然大量重复报道同一事件。去重做成四层漏斗，每层独立判据、逐层放宽：

```
raw_item ──> L2 编号实体对齐（CVE/GHSA/CNVD/CNNVD/EDB 正则集合，
│             任一并集命中即对齐；优先于 URL，防目录页误合并）
│   未命中
├──> L1 URL 规范化哈希（sha256(url)；附加 _id_compatible 守卫：
│             双方编号集合不相交则不合并）
│   未命中
├──> L3 标题指纹精确 + SimHash(64bit, Hamming≤3) 近重复
│   未命中
└──> L4 MinHash-LSH（128 perm, Jaccard≥0.7，正文 5-gram shingle，
              转载稿/洗稿合并）→ 未命中即新建 Item
```

**图 4-1 四层去重漏斗**。合并不只是"丢弃"——命中条目执行字段补全（更长的正文、更全的编号、更早的发布时间）、`source_names` 计数 +1、`reliability_score` 多源印证加分（+0.05/源，上限 +0.15），并把 raw→item 的映射记入 `DedupCluster`（含 `match_method/score`，去重决策可审计可回放）。

**真实缺陷修复案例（逻辑严谨性佐证）**：KEV 目录曾出现"34 条不同 CVE 共享同一目录 URL"→ L1 URL 哈希把它们误并成一条。修复动作：①实体对齐层（L2）优先级提到 URL 哈希之上；②URL/指纹命中增加 `_id_compatible` 守卫——双方均携带编号且集合不相交则拒绝合并；③KEV 条目改用 `cve.org` 独立详情页 URL 替代目录页。该案例已固化进代码注释与回归用例。

## 4.5 自动化编排

APScheduler 常驻 7 个任务（`scheduler/runner.py`）：`collect`(1min 扫到期源) / `enrich`(5min) / `index`(5min) / `kg`(10min) / `langgraph_pipeline`(15min 对到期源跑完整 DAG) / `daily_report`(每日 08:00) / `epss`(每 6h 批量刷新)。任务均 `max_instances=1 + coalesce=True` 防堆叠；源级断点、条目级 SAVEPOINT、worker 级 180s 超时与 error 维度自动重试共同保证"部分失败不扩散、下次调度自动补"。

> **评委看点**："≥7 类源 + 实时监测"直接拿满 15 分；分层时效表 + 实测 p50≈30min 回应"≤6h 优秀线"；KEV 误合并缺陷修复案例是"文档逻辑严谨"的加分细节。

# 第 5 章 情报富化模块详细设计

> 本章对应"富化完整性 15 分 + 富化准确率 5 分"。

## 5.1 富化维度总览

一条原始 CVE 公告只有一段英文描述，系统把它"查成一页情报档案"。10+ 维度由 8 个并发 worker 产出：

| Worker | 产出维度 | 主要数据来源 | 性质 |
|---|---|---|---|
| `scorers` | CVSS v3.1/v4.0、severity、EPSS 分数+百分位、is_kev、SSVC 决策 | 本地 cvelistV5 克隆（优先）/NVD、FIRST EPSS 批量 API、KEV、CISA vulnrichment | 确定性源，置信度上限 1.0 |
| `mappings` | CWE→CAPEC→ATT&CK / MITRE ATLAS 映射 | 本地 `data/cwe_capec.json`、`data/attack_ai.json` 映射表 | 确定性 |
| `poc` | PoC/EXP 发现 + 四级可信度 | nomi-sec 索引、trickest/cve、ExploitDB、nuclei-templates、GitHub Search（有 token 时） | 聚合索引+确定性分级 |
| `papers` | 关联论文/分析文章 | 库内互引 + arXiv + Semantic Scholar（429 熔断降级） | 检索 |
| `assets` | 受影响互联网资产测绘 | 奇安信 Hunter（无权限→`is_simulated` 降级） | 配额化外部 API |
| `nlp` | 中文标题/摘要、受影响版本区间、缓解建议、影响/利用难度、相似情报 | DeepSeek 结构化抽取 + 确定性校验器 | LLM+校验 |
| `chain` | 攻击链生成（Attack Flow 风格 JSON + 中文叙述） | CWE/AI 层确定性模板 + LLM 润色 | 模板+LLM |
| `ai_classify` | AI 相关性精判、L1–L6 层归属复核 | 规则分边界项（0.15–0.75）走 DeepSeek 精判 | LLM 二判 |

**表 5-1 富化维度×来源×性质矩阵**。此外每条情报在 ingest 阶段即获得规则分类（AI 相关度、L1–L6、OWASP LLM/ASI 标签）与优先级分（KEV×3 + EPSS×2 + CVSS + AI 相关 + 多源印证）。

## 5.2 并发编排与三阶段事务纪律

富化流水线（`enrichment/pipeline.py`）对单条 item 执行：

1. **阶段一·短事务读**：取 item、检查/写入 `_enrich_lock` 时间戳（跨进程互斥，15min 过期可被窃取防死锁）、detach 出会话；
2. **阶段二·worker 扇出**：8 个 worker `asyncio.gather` 并发，各自 180s 超时，异常收敛为 `status:error` 结果而非崩溃；worker 期**禁止持有 DB 会话**（180s LLM 调用期持行锁曾导致 21min 活跃事务锁竞争，已重构消除）；
3. **阶段三·短事务写回**：重取最新行防并发覆盖，逐 worker 做字段合并（仅覆盖空值或白名单强字段）、extra 浅合并（`_json_safe` 序列化）、子表 `delete+insert` 幂等写回、enrichment JSONB 审计合并、HITL 分流判定、指标上报。

**图 5-1 富化流水线 fan-out/合并结构图**（代码实现见 §10.3 代码清单 10-2）。

## 5.3 准确率机制（5 分关键）

准确率不是"祈祷 LLM 不编"，而是五道工程闸门：

1. **官方字段锁死**：CVSS/severity/CWE/KEV 只接受确定性权威源（cvelistV5/NVD/EPSS/KEV）写入；LLM worker 的 `fields` 对这些字段无写权限（pipeline 白名单合并规则：`epss_score/is_kev/has_poc` 等可覆盖，其余仅填空）；
2. **来源权重**：官方 1.0 > 厂商 0.95 > LLM+证据 0.8 > 聚合 0.75 > LLM 推理 0.6 > 模拟数据 0.3——每个 worker 自报 `confidence`，合并后条目级 `confidence` 取全维均值；
3. **确定性校验器闸门**：LLM 抽出的版本号必须过 `valid_version` 正则、论文相关性要过 `token_overlap` 阈值、版本区间解析走确定性 semver 比对——幻觉产物在落库前被拦；
4. **"宁可缺不可错"abstain**：低置信维度宁可 `skipped/partial` 也不硬写；全 error≥3 或均置信度 <0.4 自动进 `needs_review` 复核队列；
5. **诚实标注**：模拟测绘数据打 `is_simulated`、演示数据打 `is_demo`、worker 状态全量留痕进 `enrichment` JSONB——评委/用户随时可审计每个数字的来源与置信度。

## 5.4 特色子模块

- **PoC 四级可信度**：trusted（ExploitDB/nuclei/metasploit 白名单或 verified）/ community / suspicious（命中恶意特征：base64 解码执行、curl|bash、IEX、硬编码 IP:port、反弹 shell、certutil/bitsadmin 下载 7 类静态特征）/ malicious（付费 PoC 等）。回应 GitHub 公开 PoC 仓库存在含毒比例的现实风险；
- **资产测绘 query 生成**：仅对 AI 生态高价值产品（ollama/vllm/gradio/jupyter/mlflow/langflow/flowise/dify/ray/milvus/chromadb/lollms/xinference/sglang 等 14 个）发起 Hunter 查询，base64 编码测绘语法；无 API 权限时产出 `is_simulated` 样本并把维度置信度压到 0.3；
- **攻击链生成**：确定性优先——11 个 CWE 模板 + 6 个 AI 层模板 + AV:N 兜底规则生成三段式骨架，LLM 仅做 60–120 字中文叙述润色；产出 Attack Flow 风格 `{"stage","desc"}` JSON 供前端流程条渲染；
- **nlp worker 产出结构**：`title_zh/summary_zh`（翻译）+ `affected_versions`（受影响版本区间，逐条过 `valid_version` 正则闸门）+ `mitigation`（修复/缓解建议）+ `impact_zh/exploitability_zh`（影响面/利用难度）+ 相似情报（库内候选经 `token_overlap` Jaccard 阈值过滤）；中文源条目走确定性 `title_zh` 回填不耗 token；
- **scorers 细节**：EPSS 走 FIRST 批量 API（≤100 条/次）；SSVC 取自 CISA vulnrichment 的 automatable/exploitation/technical_impact 决策树；CVSS/CWE **优先读本地 cvelistV5 git 克隆**（免 NVD 限流，离线可复现），已回填 823 条历史缺失；
- **S2 熔断降级**：Semantic Scholar 首次 429 后进程内标记 `_s2_dead` 跳过，不拖慢整批。

# 第 6 章 情报问答模块详细设计

> 本章对应"问答完整性 15 分 + 问答深度 5 分"。

## 6.1 Agentic RAG 全流程

问答不是"向量检索 + LLM 拼 prompt"，而是一条带自主决策与多跳桥接的流水线（`rag/query_agent.py`，`_prepare` 共享于同步/流式两个入口）：

```
问题 ──> ①实体直提 extract_ids（确定性正则：CVE/GHSA/CWE/EDB/ATLAS）
     │
     ├─ 含 CVE ──> ②CVE 直连 _cve_direct（SQL 直查情报卡+PoC+映射，短路返回）
     │
     ├─ deep=False ──> 快速通道：混合检索(免重排)→直生成（实测 3.2s / TTFT 1.09s）
     │
     ▼ deep=True
  ③LLM 路由/分解 chat_structured → {route, sub_questions≤3, entities, filters}
     │   （vuln_lookup / comparison / multi_hop / trend / general）
     ├─ KEV/在野利用意图 → 确定性 _kev_facts 直查注入（绕过检索）
     ▼
  ④Agent 工具循环（≤2 轮）：模型自主调用 retrieve_intel / kg_expand /
     get_item_detail / list_kev；无 tool_calls 即停
     │   证据 <2 条 → 回退：子问题并行 retrieve（fallback_retrieve）
     ▼
  ⑤合并候选 → bge-reranker 单次重排 top-24 → 取 top-16
     ▼
  ⑥KG 扩展 entity_expand（multi_hop/comparison/trend 或实体存在时触发，
     ≤3 跳有界 Cypher：直接关联 + CVE→CWE→同弱点其他 Item 二跳桥接）
     ▼
  ⑦上下文组装：检索文本 + DB 结构化字段水合(_hydrate→_struct_line)
     + KG 事实块 + KEV 事实块
     ▼
  ⑧DeepSeek 生成（行内 [n] 引用 + 结构化输出 / 真流式 delta）
     → 置信度校准（引用覆盖+证据分）→ 低置信 abstain
     ▼
  SSE：status(步骤进度) → trace(推理链) → citations(引用) → token(流式) → done
```

**图 6-1 问答管线全流程图**。每个阶段在 `trace.steps` 落一步（含时间戳与命中数），前端可展开为"推理链"。

## 6.2 为什么必须混合检索（dense + sparse + RRF）

- **词面召回（BM42 稀疏）**：CVE-2024-37032、CWE-502、T1190、产品名这类精确标识符，dense 向量会被"语义相似"稀释，必须靠词面命中；
- **语义召回（Qwen3-Embedding-0.6B dense）**："提示注入类事件""内网风险"这类无标识符问题，只能靠语义相似；
- **融合与重排**：Qdrant 命名向量两路 prefetch（各 top-50）→ 服务端 RRF 融合 → bge-reranker 交叉编码重排 → 聚合到 item 级（同 item 取最高分块，保留 top-2 chunk 文本）。缺一边都会漏证据：纯 dense 漏编号题，纯 sparse 漏语义题。

## 6.3 KG 多跳桥接（深度分关键）

多跳问题的本质是"答案横跨多个实体"。向量检索只能找"和问题长得像的文档"，找不到"和已知实体共享弱点的其他漏洞"。系统在检索证据之外并行做**图谱扩展**（`rag/kg.py: entity_expand`）：

- **一跳**：从问题实体（CVE/CWE/产品/技术 ID）找直接关联 Item；
- **二跳桥接**：`CVE-[:HAS_CWE]→CWE←[:HAS_CWE]-其他CVE←[:HAS_CVE]-Item`，即"同弱点关联情报"——评测集里"CWE-502 反序列化还有哪些 AI 漏洞"这类题靠它命中；
- **事实序列化**：图谱事实被序列化为 `标题 [item_id] 关联:rel via cwe` 文本块进上下文，成为可解释证据链的一部分（而不是黑盒特征）；
- 另有 `path_between` 最短路径接口（`GET /api/kg/subgraph` 前端力导图）支撑"两实体间怎么连起来"的探索式验证。

## 6.4 多轮对话、双轨延迟与可解释性

**快/深双轨**（同一 `_prepare` 流水线的两个模式位）：

| 模式 | 路径 | 实测延迟 | 适用 |
|---|---|---|---|
| CVE 直连 | 实体直提命中 → SQL 情报卡短路 | 2.2–3.2s | 编号查询 |
| 快路径 deep=False | 跳过路由/Agent/KG，混合检索（免重排）直生成 | **3.2s / TTFT 1.09s** | 时效敏感 |
| 深度 deep=True | 完整链：路由→Agent 工具→重排→KG 扩展→流式生成 | p50≈11.8s | 深度分析 |

- **多轮**：`history` 随 session 传入（路由/generate 各取最近 4–6 轮），支持追问；生成端同步输出 ≤3 条 `followups` 建议追问；
- **可解释**：每题返回 `trace.steps`（逐步耗时与命中数）+ `citations`（编号/标题/URL/分数）+ 校准后 `confidence` + `abstain` 标记；答案中每个 `[n]` 引用都可回溯到具体情报卡；
- **置信度校准**：非流式 `confidence×0.6 + 最高证据分×0.4`；流式 `0.55 + top_score×0.45`；<0.25 自动前置"置信度不足"声明（abstain）。

## 6.5 评测方法（诚实口径）

`scripts/eval_qa.py` 内置 12 题自建题集（单跳事实/多跳桥接/资产/攻击链/政策/枚举四类），全部基于库内真实实体构造；判分方式为**期望关键词子串命中**；`cite_precision` 校验"答案中 [n] 编号存在于返回 citations 集合"（编号存在性校验，非内容正确性）。模块 docstring 明确声明"自建题集口径，非盲评"。评测支持 `--live` 走真实 `POST /api/qa/chat` SSE 端到端。口径细节与限制见第 14 章。

> **评委看点**："跨文档推理与深度分析"优秀档；KG 桥接是区别于普通 RAG 的硬核点；Agent 工具循环 + trace 推理链直接命中"自主决策+可解释"；CVE 直连/快路径双轨证明对延迟与深度做过工程取舍。

# 第 7 章 AI 安全知识底座

> 本章是差异化核心，同时回应赛题"构建完整 AI 安全知识底座"的原文要求。

## 7.1 三维情报立方体

普通漏洞库回答"这个 CVE 是什么"；AI 安全运营要回答"我的 AI 资产面临什么威胁"。系统把每条情报同时投影到三个正交维度：

- **L1–L6 AI 资产分层**（`core/taxonomy.py`，规则分类器入库即打分，边界项 LLM 精判）：
  L1 基础设施与推理层（GPU/CUDA/Ollama/vLLM/Triton/llama.cpp/向量库/Jupyter/MLflow）· L2 模型与数据层（越狱/注入/投毒/窃取/反演）· L3 应用与智能体层（Copilot 类产品/插件/MCP/A2A/Coding Agent）· L4 供应链层（HF 模型仓库/PyPI-npm/模型格式/分发渠道）· L5 政策与治理层（网信办/TC260/GB/EU AI Act/NIST）· L6 滥用与威胁行为（AI 赋能攻击/恶意 LLM 服务）；
- **OWASP 双标签**：LLM Top10 2025（LLM01 提示词注入…LLM10 无界消耗）+ ASI Agentic Top10（ASI01 目标劫持…ASI10 失控智能体），规则命中多标签并存；
- **MITRE ATLAS / ATT&CK**：条目携带 `atlas_techniques`（AML.T\*）与 `attack_techniques`（T\*\*\*\*），映射表附成熟度语义。

**实测分布**（`/api/stats/overview`，2026-10-17）：AI 相关条目 2,330 条，其中 L1=2,078、L2=138、L3=2,196、L4=103、L5=25、L6=13（一条情报可多层归属；未命中 AI 分类的条目不计层）——证明分类器不是摆设，大屏 L1–L6 环图是真实数据驱动。

## 7.2 知识图谱 Schema 与同步

节点：`:Item`（情报卡）、`:CVE`、`:GHSA`、`:CWE`、`:CAPEC`、`:Technique{kind:atlas|attack}`、`:Product`、`:Vendor`。
边：`Item-[:HAS_CVE]->CVE-[:HAS_CWE]->CWE`，`Item-[:MAPS_TO]->CAPEC|Technique`，`Item-[:AFFECTS]->Product`，`Item-[:MADE_BY]->Vendor`，`Item-[:HAS_GHSA]->GHSA`。

同步为 `MERGE` 幂等（`services/kg.py: sync_item`），增量任务每 10 分钟补漏；实测图谱规模 **18,593 节点 / 37,836 边**（`/api/kg/stats`，2026-10-17，随滚动采集持续增长，演示现场以当日实测为准）。

## 7.3 CVE + 非 CVE 双轨

`item_type` 区分 vuln / advisory / exploit / article / paper / policy / incident——非 CVE 情报与漏洞同库、同管线、同问答。实测构成（2026-10-17）：exploit 30,001 / vuln 14,068 / article 446 / advisory 314 / paper 123 / policy 15 / incident 4。EchoLeak 提示注入事件、ShadowRay（Ray 未认证 RCE）、MCP 投毒系列、GB 标准与网信办文件均以一等公民身份进库、进图、进问答评测集。

## 7.4 影子漏洞标注

CVE-2023-48022（ShadowRay）是典型的"disputed 但在野利用"影子漏洞——官方状态有争议，实际已遭大规模利用。系统以"disputed-but-exploited"视角收录并标注，在 KEV 类问答中作为证据链一环出现（评测集"哪些 AI 基础设施漏洞已被在野利用"一题的期望命中项之一）。这体现的是情报深度：正式目录里差点漏掉的威胁，情报系统不能漏。

> **评委看点**："AI 资产视角"是现有平台（含国际 TI 产品）无人做的垂直空白，正对命题方产品线盲区；双轨与影子漏洞证明对 AI 安全领域的理解深度；图谱规模数字证明知识底座已真实运转而非画饼。

**代码清单 10-2：富化 fan-out 与确定性合并写回（`enrichment/pipeline.py: enrich_item` 节选，约 30 行）**

```python
    # ---- 阶段2：worker 扇出（纯计算/网络，无 DB 会话）----
    async def one(name, fn):
        if wanted and name not in wanted:
            return name, None
        try:
            return name, await asyncio.wait_for(fn(item, None), timeout=180)
        except Exception as e:  # noqa: BLE001
            log.error("worker_failed", item=item_id, worker=name, error=str(e)[:200])
            return name, {"status": "error", "confidence": 0.0, "note": str(e)[:300]}

    results = await asyncio.gather(*[one(n, f) for n, f in WORKERS])
    # ---- 阶段3：短事务写回 ----
    async with sf() as db:
        item = (await db.execute(select(Item).where(Item.id == item_id))).scalar_one_or_none()
        enrichment = {**(item.enrichment or {}), **enrichment}  # 并发安全合并
        for name, res in results:
            enrichment[name] = {k: res.get(k) for k in ("status","confidence","note","ts","data_keys")}
            for k, v in (res.get("fields") or {}).items():      # 字段合并：worker 优先级低
                if v is None: continue
                cur = getattr(item, k, None)
                if cur in (None,"",[],0,0.0,False) or k in (
                    "epss_score","epss_percentile","is_kev","has_poc","ai_relevance_score"):
                    setattr(item, k, v)
            for rk, model in ROW_MODELS.items():               # 子表 delete+insert 幂等
                rows = (res.get("rows") or {}).get(rk)
                if rows:
                    await db.execute(delete(model).where(model.item_id == item_id))
```

**解读**：worker 契约（见 `common.py` docstring）规定 `run(item,ctx)` 只读 item、不直接写库，返回 `{status,confidence,note,fields,extra,rows}`；合并权由 pipeline 独占——字段只在"现值为空或字段在白名单"时覆盖，保证官方确定性数据不被 LLM 污染；`asyncio.wait_for(180)` 让 LLM 超时收敛为 `status:error` 而不是拖死整批；子表 delete+insert 使同一 item 重复富化天然幂等。这是"准确率机制"的代码层落点。

**代码清单 10-3：Agent 工具调用循环（`rag/query_agent.py: _agent_evidence` 节选，约 29 行）**

```python
async def _agent_evidence(question: str, history: list[dict], step) -> list[dict]:
    """Agent 工具调用循环：模型自主决策调用哪些工具收集证据（≤2轮）"""
    msgs = [{"role": "system", "content": AGENT_SYS},
            *[{"role": h["role"], "content": h["content"]} for h in history[-4:]],
            {"role": "user", "content": question}]
    evidence: list[dict] = []
    for rnd in range(2):
        try:
            out = await chat(msgs, tools=AGENT_TOOLS, max_tokens=1024)
        except Exception as e:
            step("agent_error", error=str(e)[:120]); break
        tcs = out.get("tool_calls") or []
        if not tcs:
            step("agent_stop", round=rnd, reason=out.get("finish_reason")); break
        msgs.append({"role": "assistant", "content": out.get("content") or "",
                     "tool_calls": [{"id": t["id"], "type": "function",
                                     "function": t["function"]} for t in tcs]})
        results = await asyncio.gather(*[
            _exec_tool(t["function"]["name"], json.loads(t["function"]["arguments"] or "{}"))
            for t in tcs])
        for t, res in zip(tcs, results):
            step("tool_call", tool=t["function"]["name"],
                 args=str(t["function"]["arguments"])[:150], hits=len(res["evidence"]))
            msgs.append({"role": "tool", "tool_call_id": t["id"],
                         "content": json.dumps(res["summary"], ensure_ascii=False)[:1200]})
            evidence.extend(res["evidence"])
    return evidence
```

**解读**：标准 ReAct 循环的紧凑实现——模型每轮返回 tool_calls，本轮所有工具 `gather` 并行执行，结果以 ≤1200 字符 summary 回灌（防上下文膨胀），`evidence` 进证据池；`step("tool_call",…)` 把每次调用实时推给前端推理链。轮次硬上限 2 + 无 tool_calls 提前退出 + LLM 异常收敛 break，是"自主但不失控"的边界。

**表 12-2 分源时效表**。两点诚实说明：
1. **整体 p50 被历史回填拉偏**：本表统计的是"情报原披露时间→入我库时间"。10 月中旬系统对 NVD/ExploitDB 做了全量历史回填，数万条数月/数年前披露的条目把整体分位数拉到 ~84 小时——这不代表新情报时效。**增量通道的真实时效看 cvelistV5（30.1min）与 nvidia_psirt（0.5min）两行**，它们反映"发布后下一个轮询周期内入库"的准实时能力，核心链路设计 ≤1h，远优于 6h 满分线。
2. **金丝雀 e2e**：合成情报注入→详情卡 1.3s→全链路（富化+索引）可检索 **43.7s**——链路内部处理时效的硬证据。

## 12.3 问答性能实测

| 口径 | 数值 | 出处 |
|---|---|---|
| 快路径（deep=False） | 总时长 3.2s，TTFT 1.09s | SSE 实测 |
| CVE 直连（含编号问题短路） | 2.2–3.2s | eval 题 #1/#3/#4 |
| 深度模式延迟 | 中位 **≈11.8s** / p95 27.5s（脚本口径 p50=14.2s） | eval_qa.json 12 题 |
| 多跳题 p50 | ≈20s（Agent 工具循环+KG 扩展+重排） | eval_qa.json |
| 准确率 | 整体 97.9% / 多跳 95.8% / 引用 100% | eval_qa.json |

**延迟归因**：深度模式耗时主要在 ①Agent 工具循环 1–2 轮 LLM 决策（每轮一次 DeepSeek 调用+并行工具执行）；②跨候选合并重排（CPU 交叉编码 top-24）；③KG 扩展 Cypher；④生成 token 流。这是"用延迟换深度"的设计内行为：快路径 3s 满足时效敏感场景，深度模式以流式输出把感知延迟降到 TTFT ~1s，等待过程用真实推理链填充。trace_coverage 66.7% 低于 100% 的原因同样如实说明：CVE 直连/事实直取类问题走短路（2 步即返回），并非推理链缺失。

## 12.4 富化准确率实测与失分归因

整体 **准确率 91.6% / 召回率 89.0%**（n=30）。距自设 95% 目标的差距归因（逐条可追溯至 `eval_enrichment.json` 明细）：

1. **EPSS 时效漂移**（最大失分项，acc 82.8%/79.3%）：EPSS 分数每日更新，我库为富化时点值、真值为评测时点值——多个 `diff` 样本实为时间差而非错误（如 CVE-2022-0995 0.009→0.969 是官方分数跳变）。已通过每 6h `job_epss_refresh` 批量刷新收窄（实测 186 条/41s），残余偏差属口径内噪声；
2. **missing ≠ wrong**：cvss/severity 的 `missing`（我空真有）主要因该条目入库时 NVD 尚未发布评分（awaiting analysis 数据真空，详见第 14 章），或源未提供。missing 计入召回但不计准确率分母——这也是"宁可缺不可错"策略的必然代价：我们主动放弃了"硬编一个值"的选项；
3. **亮点**：`is_kev` 混淆矩阵 13/0/17/0 全对、`cwe_ids` 准确率 100%、`cvss_v31_score` 准确率 95.0%——"官方字段锁死"机制在可判字段上兑现了高准确率。

# 第 14 章 评测口径与已知限制（诚实声明）

> 本章集中声明全部评测口径与已知限制。**我们认为：在准确率评分的赛题里，主动交代口径本身就是准确率意识的一部分。**

## 14.1 评测口径声明

1. **问答评测为自建题集 + 关键词命中口径**：`scripts/eval_qa.py` 内置 12 题均基于库内真实实体构造，判分为期望关键词子串命中率；`cite_precision` 校验的是"答案中 [n] 引用编号存在于 citations 集合"（编号存在性），**非引用内容正确性**。该口径适用于回归与演示，**非盲评**；脚本 docstring 已就此声明，对外引用均已注明。
2. **富化评测 n=30 + 容忍度口径**：`eval_enrichment.py` 抽 30 条已富化条目，以 FIRST EPSS / CISA KEV / NVD 三源实时数据为地面真值；判定容差 EPSS±0.05、CVSS±0.1、CWE 集合 IoU≥0.5；准确率分母为"真值非空且我方已填"的字段对，`is_kev` 布尔单独报混淆矩阵。**非盲评，样本量有限**。
3. **时效指标口径**：`stats/freshness` 为"原披露时间→入库"滞后，含历史回填样本时整体分位数被拉偏（§12.2 已说明）；增量时效以 cvelistV5/nvidia_psirt 分源数据为准。
4. **模拟与演示数据全量标记**：Hunter 测绘无 API 权限时资产维度产出 `is_simulated` 样本（维度置信度压至 0.3，前端标注"模拟数据"）；演示种子条目 `extra.is_demo=true`、`source_names=["demo"]`，且时效看板统计中排除 is_demo/canary 条目。
5. **历史失分口径**：金丝雀条目默认跑完自动清理（`--keep` 保留）；评测中 `missing`（我空真有）计召回不计准确率、`no_truth`（真值空）不计失分。

## 14.2 已知限制

| # | 限制 | 影响 | 缓解/规划 |
|---|---|---|---|
| 1 | MinHash-LSH 为进程内单例 | 多进程部署不共享；重启后需从 DB 重建索引（`_load_lsh` 已做，上限 5 万条） | 生产多副本场景拟迁移至 PG 持久化 band 签名或外部 LSH 服务 |
| 2 | CVE-2026-* awaiting analysis 数据真空 | NVD 对最新 CVE 常延迟发布 CVSS/CWE，对应字段为"真空"而非系统缺漏 | scorers 优先读 cvelistV5 本地克隆补 CNA 侧数据；字段留空优于编造 |
| 3 | GHSA 采集 403 | 未配置 GITHUB_TOKEN 时 GHSA 源暂停（24 次连续失败记录在案） | 提供 token 即恢复；当前由 OSV/cvelistV5 覆盖同信息域 |
| 4 | Hunter 测绘为模拟降级 | 资产暴露数字非真实测绘值 | 管线/语法/落库全真实，接正式 key 即切换；`is_simulated` 全程标记 |
| 5 | 部分 RSS 源被 WAF/证书拦截 | freebuf/knownsec/aqniu 等当前 0 产出 | 记错不阻塞；健康页公开失败状态；可加自定义头/镜像重试 |
| 6 | 深度问答多跳延迟 ~20s | 交互耐心成本高 | 快路径 3s 双轨 + 流式 TTFT 1.09s + 推理链填充等待；可缓存热点子图 |
| 7 | 评测样本规模有限（QA n=12 / 富化 n=30） | 分数存在小样本波动 | 决赛前扩充盲评集并请第三方标注 |
| 8 | Prometheus 指标为进程内计数 | API 重启后计数归零 | 演示前重启则计数从 0 起； gauge 类（金丝雀/KG 规模）不受影响 |

# 第 15 章 总结与展望

**已实现能力一句话收口**：11 类 41 源准实时监测 → 四层去重 → 8 worker 并发富化 10+ 维 → 向量+图谱双底座 → Agentic RAG 多跳问答（整体 97.9%/多跳 95.8%）→ 日报自动生成与 SSE 实时推送——全流程无人值守、全数字实测可查、全降级有标记。

**展望（按优先级）**：

1. **评测集扩容与盲评化**：QA 题集扩至 50+ 并引入第三方标注；富化评测扩样本并纳入更多字段（版本区间、PoC 可用性）；
2. **秒级通道**：GHSA webhook / cvelistV5 GitHub webhook 推送替代轮询，把准实时层压到秒级；
3. **Hunter 正式权限接入 + 告警推送/工单联动**：把"模拟降级"的最后一环换成真数据，并把高危情报推到企业 IM/工单系统；
4. **LSH 持久化与多实例扩展**：MinHash 签名落 PG，支撑多副本部署；
5. **LSH→向量近重合并**：复用已有 embedding 做第五层语义去重，进一步压缩"同一漏洞不同表述"的误新建率。
